### 🔁 Ongoing / Recurring
- **Daily coordinator log review** — Each day, pull the previous 24h of logs from the NAS (`python skills/synology.py ssh "sudo docker logs enphase-juicebox-coordinator --since 24h 2>&1 | tail -500" --sudo`) and audit:
  - Did the 04:00 tariff fetch + schedule push succeed? (`status=ok`, `juicebox_ok=True`)
  - Did the 21:00 calendar check + immediate JuiceBox push run cleanly?
  - Did pre-peak (Savings → Self-Consumption) and post-peak (Self-Consumption → Savings) battery mode switches fire on weekdays at the tariff-derived times, with confirmation reads matching the target?
  - Did the surplus solar monitor activate when SOC ≥ 95% and production > consumption, and revert correctly?
  - Any tracebacks, retries, email failure alerts, or tariff parse fallbacks?
  - Compare actual JuiceBox charging windows vs. expected (avoid 16:00–19:00 peak; use super off-peak 10:00–15:00 in winter / overnight when calendar enables it).

  For each anomaly, file a fix on this roadmap and ship it the same day so the next 24h cycle improves. Sunday weekly report (already emailed at 07:17 AZ) is the rollup; this task is the daily granular check.

- **🐛 Alert emails said "unhandled errors in a TaskGroup (1 sub-exception)" and nothing else (2026-09-08)** — Every mode-switch failure alert since 2026-09-03 reported only that string, hiding the real cause (`httpx.ConnectError: [Errno -3] Temporary failure in name resolution`) one level down inside an anyio exception group. The MCP SSE transport (`sse_client` + `ClientSession`) runs in an anyio task group, so any connection failure escapes the `async with` as a `BaseExceptionGroup` whose `str()` is that fixed, useless sentence. Fix: new `errors.py` with `describe_exception()` (flattens groups to their leaves, dedupes, falls back to the class name when a message is empty) and `surfacing_errors()` (an async CM that re-raises the flattened cause, preserving the leaf's type so callers can still catch `httpx` errors, and never rewriting `CancelledError`). Wired into both MCP clients and every exception-stringifying site in `server.py`, `coordinator.py`, `calendar_check.py`, `battery_mode.py`. **Second bug fixed by the same change:** `Failed to send failure alert email:` logged with an empty message, because `str(httpx.ConnectTimeout())` is `""` — `describe_exception` now falls back to the class name and the chained cause. **Third improvement:** the alert's recovery advice ("run `switch_battery_mode` to retry") is useless during a network outage, so `_looks_like_connectivity_failure()` now appends a Diagnosis section pointing at the container → DNS → NAS default route chain. Also collapsed six duplicated SSE handshakes in `enphase_mcp.py` into one `_call_tool()` helper, and two in `juicebox_mcp.py`. 31 new tests (214 total).
- **🐛 This coordinator was crash-looping — 8322 restarts, unnoticed (2026-08-08)** — found while fixing the same fault in `claude-enphase` and `enphase-nirvana-coordinator`; all three of the Enphase stack's containers were down simultaneously. Dying at import with `AttributeError: 'Server' object has no attribute 'list_tools'` (`server.py:284`) because `requirements.txt` said `mcp>=1.0.0` and mcp **2.0.0** removed the low-level `Server` decorators this server is built on (2.0 exposes `add_request_handler` instead). - **Surface real Enphase errors instead of misleading "got None" (2026-06-02)** — A scheduled pre-peak switch failed with `Enphase did not confirm target mode (got None, expected 'self-consumption')`. Root cause: when claude-enphase returns a structured error dict (e.g. `{"error": "token expired"}` / `{"status":"error",...}` on DNS failure, expired token, or Enphase 5xx), `enphase_mcp` only caught `isError` and `"Error:"`-prefixed text — the error dict passed through `json.loads`, `_extract_mode` returned None, and the alert showed the unhelpful "got None". Fix: new `enphase_mcp._raise_if_error_payload` / `_parse_tool_result` raise the real cause on any error-shaped payload, so it lands in retry logs and the failure email. Also: `battery_mode.switch_to` now raises an actionable error including the raw set/verify payloads when no mode is recognizable (instead of a bare "got None"). 16 new tests (183 total). **Operational note:** the underlying outage that triggered the alert (likely an expired Enphase token or DNS) must still be cleared on the NAS — this change makes the next failure email name the real cause.
